# FLUX 3 Technique Bank

Proven techniques and prompt patterns for Flux 3 video generation (bfl_flux3_* tools).
Source: production sessions, July 2026.

## Prompt Architecture

Flux 3 prompts are read by a reasoning harness that expands them. Write plain prose
at whatever length the brief deserves. A single line is valid. Don't restyle the
user's wording — the harness does that, and stacking a second rewrite drifts intent.

Order: subject, distinguishing visual specifics, action, camera, lighting,
environment, audio, style. Audio is generated by default whether or not you
mention it — name layers explicitly (ambient, music, speech) or say "no music."

## Multi-Shot Structure

Format that produces real hard cuts:

```
A [N]-shot cinematic sequence, [genre/mood].

SHOT ONE: [shot type] [subject + action]. [environment]. [lighting]. [camera]. [audio layers].

HARD CUT.

SHOT TWO: [shot type] [subject + action]. [environment]. [lighting]. [camera]. [audio layers].

HARD CUT.

SHOT THREE: [shot type] [subject + action]. [environment]. [lighting]. [camera]. [audio layers].

No on-screen text, no subtitles.
```

Rules:
- Consecutive shots MUST contrast in scale, location, or color. Near-identical
  coverage blends into a continuous take and the cut won't read.
- "one continuous unbroken shot" gets an uncut take.
- Each shot needs its own audio description — the model layers them.
- End with "No on-screen text, no subtitles" to prevent burned-in text.

## Proven Prompt: Cyberpunk Hacker Sequence (15s, 16:9, 720p)

Three-beat narrative: approach → command → payoff. Each beat ~5 seconds.

```
A three-shot cinematic sequence, cyberpunk night.

SHOT ONE: Medium tracking shot following a young woman in a dark technical
jacket with a high collar, walking with calm purpose down a rain-slicked
cyberpunk market street. Neon signage in cyan and magenta stacks above her,
casting shifting color across her face. Steam rises from street vendors. Her
eyes flick briefly to the right — scanning something off-screen. Handheld
camera at her shoulder. Rain on pavement, crowd murmur, sizzling food, a low
analog synth drone.

HARD CUT.

SHOT TWO: Extreme close-up on her hands holding a slim phone at chest height.
The screen shows a dark terminal interface with a single amber prompt line and
a blinking cursor. Her thumb types one short command. Output scrolls rapidly —
lines of monospace text, a progress bar filling. The screen pulses once with a
warm amber confirmation glow. Her expression is unreadable, bored almost. The
crisp tap of glass, a soft digital chirp as the command executes, then a quiet
success tone. Shallow depth of field, neon bokeh behind.

HARD CUT.

SHOT THREE: Wide shot from across the street. A sleek black car's headlights
flash twice and the engine hums to life, cutting white beams through the rain.
The woman walks past it without breaking stride, sliding the phone back into
her jacket. The synth drone resolves into a single low note. Rain, the engine's
idle purr, the distant city.

No on-screen text, no subtitles.
```

Why this works:
- Shot 1 (medium, street) → Shot 2 (extreme close-up, hands) → Shot 3 (wide,
  across street) — strong scale contrast at every cut.
- Phone already in hand at shot 2 start — avoids the extraction problem.
- Screen described as visual object (glow, cursor, scrolling shapes), not content.
- Each shot has distinct audio layers that transition (street noise → digital
  chirp → engine + rain).
- The "bored almost" expression direction sells the character through nonchalance.

## Device Screens at 720p

Text won't be legible. Don't try. Describe the screen as a visual object:
- "dark terminal interface, amber prompt line, blinking cursor"
- "lines of monospace text scrolling, a progress bar filling"
- "the screen pulses with a warm confirmation glow"

The audience's brain fills in "terminal" from the shape. Specifying actual
readable text produces garbled output or burned-in subtitles.

If you need a specific UI to be recognizable, generate a clean still frame
first (image_generate), then use bfl_flux3_image_to_video with that as frame 0.

## Hand-Object Interaction

The hardest problem for any video model. Mitigations ranked by reliability:
1. Start the shot with the object already in hand (most reliable)
2. Use a cut to hide the transition (shot A: empty hands → HARD CUT → shot B: holding object)
3. Describe the action in broad terms only ("she pulls out her phone") and hope
4. Never: close-up of hand reaching into pocket/bag and extracting a small object

## Duration Budgeting

| Shots | Recommended duration | Per-shot budget |
|---|---|---|
| 1 | 5-10s | 5-10s |
| 2 | 10s | ~5s each |
| 3 | 15s | ~5s each |
| 4+ | 20s or split into continuations | <5s gets rushed |

Under 4 seconds per shot, actions feel truncated. The model needs time to
establish, execute, and hold each beat.

## Continuation Chaining

For sequences longer than 20 seconds:
1. Generate segment 1 (max 15s for continuation input, max 20s standalone)
2. Use bfl_flux3_video_continuation with the output mp4 (must be ≤50MB, ≤15s)
3. Open the prompt with "Continue this video from its final frames:"
4. Re-establish the subject and the moment the clip ended on
5. Describe what happens next — duration is the NEW segment only

Plan each segment as a self-contained narrative beat. Don't split mid-action.

## Audio Layering

Audio generates by default. Name each layer separately:
- Ambient: "rain on pavement, distant crowd murmur"
- Music: "a low analog synth drone" or "no music"
- SFX: "the crisp tap of glass, a soft digital chirp"
- Speech: only works if a speaker is visible on camera. Quote the line,
  describe the speaker, add "no on-screen text, no subtitles."

Transitions between shots: describe how audio changes at each cut
("the synth drone resolves into a single low note").

## Generation Timing

- Submit returns a job id immediately. The video does not exist yet.
- Generation takes several minutes. A long "Generating" phase is normal.
- bfl_flux3_get_result blocks while the job runs — one call can take minutes.
- If it returns still-generating, call again immediately. No sleeping.
- Jobs survive client restarts. Re-poll the same id; never resubmit.
- Nothing reaches disk before Ready. Checking folders mid-run tells you nothing.
